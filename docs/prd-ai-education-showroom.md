# AI 교육앱 쇼룸 PRD

## 1. 제품 개요

### 제품명

AI 교육앱 쇼룸

### 한 줄 설명

교사 연수에서 만들 수 있는 교육용 앱 아이디어를 난이도별로 탐색하고, 각 앱의 체험 흐름을 실제 서비스처럼 확인하는 Next.js 기반 미리보기 라이브러리.

### 제품 목적

이 프로젝트는 완성형 SaaS가 아니라 교사 연수용 프로토타입 전시관이다. 연수생이 "AI 바이브코딩으로 어떤 교육앱을 만들 수 있는지"를 빠르게 이해하고, 수업 적용 아이디어를 얻도록 돕는다.

앱은 실제 AI API, 로그인, 데이터베이스, 외부 저장소를 기본으로 연결하지 않는다. 사용자가 입력하거나 업로드한 것처럼 보이는 UI를 제공하고, 실행 버튼을 누르면 미리 준비된 목업 결과가 생성된 것처럼 표시한다.

## 2. 사용자와 사용 맥락

### 1차 사용자

교사 연수에 참여하는 연수생.

### 2차 사용자

연수를 진행하는 강사.

### 사용자 특성

- 전문 개발자가 아닐 수 있다.
- AI Studio, Gemini Canvas, Vercel, Supabase, Next.js 같은 도구를 처음 접할 수 있다.
- 실제 개발 세부보다 "내 수업에 이런 앱을 만들 수 있겠다"는 감각이 중요하다.
- 짧은 시간 안에 앱 아이디어, 난이도, 수업 활용 장면을 직관적으로 파악해야 한다.

## 3. 제품 콘셉트

### 핵심 성격

- 연수용 앱 아이디어 전시관
- 교육용 앱 프로토타입 라이브러리
- 실제 기능처럼 체험되는 정적 목업 서비스
- AI 바이브코딩 수업 예시 자료

### 핵심 사용자 흐름

1. 사용자가 랜딩페이지에 접속한다.
2. 접속 코드를 입력한다.
3. 코드가 맞으면 앱 라이브러리로 이동한다.
4. 난이도, 카테고리, 검색어로 앱을 탐색한다.
5. 앱 카드를 클릭해 라이트박스에서 상세 정보를 본다.
6. 라이트박스에서 같은 카테고리 앱을 넘겨본다.
7. 체험 열기 버튼으로 개별 앱 체험 페이지에 들어간다.
8. 입력, 선택, 업로드 UI를 조작한다.
9. 실행 버튼을 누르면 로딩 후 목업 결과가 표시된다.
10. 다시 체험하거나 라이브러리로 돌아간다.

## 7. 앱 구성 기준

앱은 개발 난이도를 기준으로 `하`, `중`, `상`으로 나눈다. 난이도는 수업 가치가 아니라 구현에 필요한 기술 범위를 의미한다.

| 난이도 | 기준 | 쇼룸에서 보여줄 방향 |
| --- | --- | --- |
| 하 | HTML, CSS, JavaScript, 정적 데이터 | 바로 만들 수 있는 수업 도구 |
| 중 | 단일 API 키 기반 이미지 생성, 챗봇, 텍스트 생성 | API 연결 후 확장되는 AI 수업 도구 |
| 상 | 여러 API, 외부 서비스, 인증, 저장소, 프로젝트 구조 | 장기 프로젝트와 외부 연동 구조 |

### 하: 기본 코드 기반 앱

| 앱 | 수업 장면 | 핵심 기능 |
| --- | --- | --- |
| 수업 타이머 스테이션 | 모둠 활동 시간 관리 | 타이머, 단계 안내, 발표 순서 |
| 퀴즈 카드 빌더 | 형성평가와 복습 | 문제 카드, 정답 확인, 난이도 표시 |
| 독서여권 스탬프북 | 독서 기록 | 나라/장르 선택, 생각 기록, 스탬프 |
| 카드뉴스 캠페인 메이커 | 사회 문제 캠페인 | 4장 카드뉴스 초안, 주장과 근거 정리 |
| 과학 실험 절차 카드 | 탐구 수업 | 준비물, 단계, 관찰 질문 |

### 중: 단일 API 키 활용 앱

| 앱 | API 유형 | 핵심 기능 |
| --- | --- | --- |
| 그림책 장면 제작기 | 이미지 생성 | 주제, 인물, 배경 기반 장면 이미지 |
| AI 질문 생성 도우미 | 챗봇, 텍스트 생성 | 수준별 질문 생성 |
| 발표 피드백 코치 | 챗봇, 텍스트 생성 | 발표 대본 피드백과 수정 문장 |
| AI 발명 설계소 | 이미지 생성 | 아이디어를 설계도와 시제품 이미지로 확장 |
| 생활 안전 웹툰 생성기 | 이미지, 텍스트 생성 | 안전 주제를 4컷 웹툰 흐름으로 변환 |

### 상: 외부 연동과 프로젝트형 앱

| 앱 | 연동 범위 | 핵심 기능 |
| --- | --- | --- |
| 마이크로비트 교실 IoT 대시보드 | 하드웨어, 클라우드 DB, 알림 API | 센서값 수집, 알림, 실시간 대시보드 |
| 탐구 프로젝트 포트폴리오 | 인증, DB, 파일 저장 | 팀별 산출물 저장, 피드백, 발표 자료 |
| 지역 문제 데이터 맵 | 지도 API, 공공데이터, 스프레드시트 | 지역 데이터를 지도와 카드로 시각화 |
| 학습 분석 리포트 메이커 | LMS, 스프레드시트, LLM API | 학습 기록 분석, 개인별 리포트 |
| 학급 챗봇 허브 | RAG, 파일 저장, 다중 모델 API | 학급 자료 기반 챗봇과 권한 관리 |

## 8. 페이지 요구사항

### 8.1 랜딩페이지

#### 목적

쇼룸의 첫인상을 제공하고 접속 코드를 입력받는다.

#### 요구사항

- 첫 화면에서 제품명과 입장 UI가 명확해야 한다.
- 접속 코드 입력창과 입장 버튼을 제공한다.
- 올바른 코드를 입력하면 `/library`로 이동한다.
- 잘못된 코드를 입력하면 오류 메시지를 표시한다.
- 세션이 유지되는 동안 `/library`, `/apps/[slug]` 접근을 허용한다.

#### UI 원칙

- 첫 화면은 쇼룸의 성격이 바로 드러나야 한다.
- 사용자에게 구현 설명을 늘어놓지 않는다.
- 버튼과 입력창은 연수 현장에서 바로 사용할 수 있을 만큼 커야 한다.

### 8.2 앱 라이브러리

#### 목적

연수생이 앱 아이디어를 난이도와 수업 장면 기준으로 탐색하게 한다.

#### 요구사항

- 앱 목록을 카드 그리드로 표시한다.
- 모바일 1열, 태블릿 2열, 데스크톱 3~4열을 지원한다.
- 난이도 필터 `전체`, `하`, `중`, `상`을 제공한다.
- 카테고리 필터를 제공한다.
- 앱 이름, 태그, 기술 기준 검색을 제공한다.
- 앱 수, 난이도 단계, 수업 영역 요약을 보여준다.
- 앱 카드를 클릭하면 라이트박스가 열린다.

#### 카드 구성

- 썸네일
- 난이도 배지
- 카테고리
- 추천 학년
- 앱 제목
- 짧은 설명
- 개발 기준
- 수업 활용
- 태그

### 8.3 라이트박스

#### 목적

페이지를 떠나지 않고 앱의 주요 정보와 미리보기 이미지를 빠르게 확인하게 한다.

#### 요구사항

- 앱 카드 클릭 시 중앙 모달을 연다.
- 배경은 어둡게 처리한다.
- 왼쪽 또는 상단에 이미지 미리보기를 크게 표시한다.
- 이미지 캐러셀을 제공한다.
- 같은 카테고리 앱을 이전/다음 버튼으로 넘길 수 있다.
- 닫기 버튼과 ESC 닫기를 지원한다.
- 체험 열기 버튼으로 `/apps/[slug]`로 이동한다.

### 8.4 앱 체험 페이지

#### 목적

각 앱 아이디어를 실제 앱처럼 짧게 체험하게 한다.

#### 공통 구성

- 앱 소개
- 입력 영역
- 선택 필드
- 업로드 목업 영역
- 실행 버튼
- 로딩 상태
- 결과 영역
- 다시 체험하기 버튼

#### 공통 동작

1. 사용자가 입력 또는 선택을 한다.
2. 실행 버튼을 누른다.
3. 앱별 로딩 문구가 2~3초 동안 표시된다.
4. 정적 목업 결과가 생성된 것처럼 나타난다.
5. 결과 영역에 사용자가 입력한 일부 내용을 반영한다.
6. 결과 하단에 체험용 예시 결과임을 알린다.

## 9. 데이터 요구사항

### 앱 데이터 타입

```ts
export type AppItem = {
  slug: string;
  title: string;
  category: string;
  shortDescription: string;
  longDescription: string;
  thumbnail: string;
  previewImages: string[];
  tags: string[];
  targetGrade: string;
  difficulty: "하" | "중" | "상";
  buildBasis: string;
  lessonUse: string;
  demoType: string;
  route: string;
  actionLabel: string;
  fields: DemoField[];
  loadingMessages: string[];
  mockResult: MockResult;
};
```

### 데이터 원칙

- 앱 목록은 `src/data/apps.ts`에서 관리한다.
- 실제 API 응답처럼 보이는 값도 정적 데이터로 둔다.
- 사용자가 입력한 `topic`, `level`, `notes`는 결과 화면 일부에 반영할 수 있다.
- 라우팅은 `slug`를 기준으로 생성한다.
- 존재하지 않는 slug는 404 처리한다.

## 10. 썸네일 요구사항

### 파일 기준

- 파일 형식: PNG
- 위치: `public/visuals/generated-thumbnails/`
- 연결: 각 앱의 `thumbnail`과 `previewImages[0]`

### 스타일 기준

- 하나의 통일된 일러스트 스타일을 사용한다.
- 스타일은 귀여운 2D 벡터 일러스트, 둥근 오브젝트 마스코트, 깨끗한 교육용 썸네일 톤으로 한다.
- 앱별 캐릭터, 소품, 지배 배경색은 명확히 달라야 한다.
- 코발트는 브랜드 공통 포인트로만 사용하고, 모든 썸네일을 코발트 중심으로 만들지 않는다.
- 카드 그리드에서 멀리 봐도 앱이 구분되어야 한다.

| 앱 | 지배 색상 방향 | 시각 소재 |
| --- | --- | --- |
| 수업 타이머 스테이션 | 레몬 옐로우 | 타이머 마스코트, 활동 토큰 |
| 퀴즈 카드 빌더 | 민트 그린 | 카드 더미 마스코트, 체크 칩 |
| 독서여권 스탬프북 | 라벤더 퍼플 | 여권 마스코트, 책, 스탬프 |
| 카드뉴스 캠페인 메이커 | 코랄 레드 | 메가폰, 빈 카드뉴스 패널 |
| 과학 실험 절차 카드 | 아쿠아 시안 | 비커, 관찰 카드, 돋보기 |
| 그림책 장면 제작기 | 피치 핑크 | 열린 그림책, 붓, 별 |

| 발표 피드백 코치 | 인디고 블루 | 마이크, 발표 보드, 피드백 칩 |
| AI 발명 설계소 | 오렌지 | 전구, 설계도, 시제품 |

| 마이크로비트 교실 IoT 대시보드 | 딥 틸 | 센서, 연결선, 대시보드 |
| 탐구 프로젝트 포트폴리오 | 올리브 그린 | 폴더, 팀 보드, 산출물 카드 |
| 지역 문제 데이터 맵 | 살몬 핑크 | 지도, 위치 핀, 데이터 카드 |
| 학습 분석 리포트 메이커 | 바이올렛 | 리포트, 차트, 학습 카드 |
| 학급 챗봇 허브 | 네이비 | 챗봇, 자료 폴더, 연결 노드 |

### 금지사항

- 썸네일 안에 읽을 수 있는 텍스트, 글자, 숫자를 넣지 않는다.
- 로고, 워터마크를 넣지 않는다.
- 모든 썸네일을 같은 흰 배경, 같은 코발트 비율, 같은 구도로 만들지 않는다.
- 3D 미니어처 렌더처럼 보이게 만들지 않는다.

## 11. 디자인 요구사항

### 전체 톤

- 세련되고 깔끔한 교육용 쇼룸
- 교사가 부담 없이 탐색할 수 있는 밝은 인터페이스
- 카드 그리드 중심의 정보 구조
- 지나치게 장식적인 랜딩 페이지보다 실제 탐색 경험 우선

### UI 규칙

- Tailwind CSS 기반으로 구현한다.
- Pretendard를 기본 폰트로 사용한다.
- 그라데이션은 사용하지 않는다.
- 카드 안에 카드가 중첩되는 구조를 피한다.
- 텍스트는 모바일과 데스크톱에서 버튼이나 카드 밖으로 넘치지 않아야 한다.
- 아이콘은 가능한 경우 lucide-react를 사용한다.
- 버튼은 목적이 명확해야 한다.
- 사용자에게 구현 방식을 설명하는 문구를 화면에 노출하지 않는다.

### 사용자 노출 문구 원칙

- 최종 사용자가 보는 문구는 제품 언어로 쓴다.
- 구현 설명, 작업 보고, 메타 설명처럼 보이는 문장은 UI에 넣지 않는다.
- 예: "정리했습니다", "구성했습니다", "배치했습니다", "비교할 수 있도록" 같은 표현은 UI에 쓰지 않는다.

## 12. 목업 결과 원칙

실제 API를 연결하지 않으므로 모든 결과는 정적 목업 데이터로 보여준다.

### 원칙

- 사용자가 입력한 내용 일부를 결과 문장에 반영한다.
- 버튼 클릭 직후 결과를 바로 보여주지 않는다.
- 앱별 로딩 문구를 보여준다.
- 결과는 실제 생성물처럼 자연스럽게 구성한다.
- 결과 하단에는 체험용 예시 결과임을 알린다.
- 사용자가 실제 AI 생성 결과로 오해하지 않게 한다.

### 로딩 문구 방향

- 앱별 맥락과 맞아야 한다.
- 짧고 직접적인 문장으로 쓴다.
- 과도한 기술 용어를 피한다.

## 13. 비기능 요구사항

### 반응형

- 모바일, 태블릿, 데스크톱을 지원한다.
- 연수 현장에서 스마트폰으로 접속해도 앱 탐색이 가능해야 한다.

### 접근성

- 버튼과 입력창은 충분히 큰 클릭 영역을 가진다.
- 카드와 텍스트 대비가 명확해야 한다.
- 라이트박스는 ESC로 닫을 수 있어야 한다.
- 이미지에는 앱 맥락에 맞는 대체 텍스트를 제공한다.

### 성능

- 라이브러리 페이지는 빠르게 로딩되어야 한다.
- 썸네일은 Next.js Image 또는 이에 준하는 최적화 흐름으로 사용한다.
- 필요 이상으로 큰 배경 비디오를 사용하지 않는다.

### 배포

- GitHub 저장소와 Vercel을 연결한다.
- main 브랜치 push 시 자동 배포되도록 한다.
- Vercel 환경변수에 `TRAINING_ACCESS_CODE`를 등록한다.

## 14. 완료 기준

### 랜딩페이지

- 접속 코드 입력창이 있다.
- 올바른 코드를 입력하면 `/library`로 이동한다.
- 잘못된 코드를 입력하면 오류 메시지가 표시된다.
- 세션이 유지되면 보호된 페이지에 접근할 수 있다.

### 라이브러리

- 15개 앱 카드가 표시된다.
- 난이도 필터가 작동한다.
- 카테고리 필터가 작동한다.
- 검색이 작동한다.
- 카드 클릭 시 라이트박스가 열린다.
- 카드 썸네일은 앱별로 구분되는 PNG 이미지다.

### 라이트박스

- 이미지 미리보기가 표시된다.
- 앱 설명, 난이도, 카테고리, 수업 활용 정보가 표시된다.
- 이전/다음 앱 탐색이 작동한다.
- 닫기 버튼과 ESC 닫기가 작동한다.
- 체험 열기 버튼이 앱 페이지로 이동한다.

### 앱 체험 페이지

- 각 앱은 고유 URL을 가진다.
- 입력, 선택, 업로드 목업 UI가 있다.
- 실행 버튼을 누르면 로딩 상태가 표시된다.
- 목업 결과가 표시된다.
- 다시 체험하기가 가능하다.

### 품질 검증

- `npm run lint`가 통과한다.
- `npm run build`가 통과한다.
- 주요 화면을 브라우저에서 확인한다.
- 모바일과 데스크톱에서 텍스트 겹침이 없어야 한다.

## 15. 구현 메모

- 앱 구성 기준은 `docs/app-reconfiguration-plan.md`를 따른다.
- PRD와 실제 앱 데이터가 충돌할 경우 현재 구현 대상은 `src/data/apps.ts`의 15개 앱을 기준으로 한다.
- 초기 버전은 단순한 정적 구조를 우선한다.
- 추후 실제 API나 Supabase를 붙일 때도 현재 쇼룸의 빠른 탐색 경험을 해치지 않는 방향으로 확장한다.
